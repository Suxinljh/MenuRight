## 「右键功能都没出现」的真因:扩展和主应用来自**两份不同的 .app**

日志(决定性证据,`log show --predicate 'subsystem == "xin.ljhsu.MenuRight"'`):

```
MenuRightFinder[4488] menu(for:) returning menu with 9 items          ← 菜单其实建出来了
MenuRightFinder[4488] peer REJECTED peer executable path mismatch:
    got=/Applications/MenuRight.app/Contents/MacOS/MenuRight
    expected=/Users/suxin/Applications/MenuRight.app/Contents/MacOS/MenuRight
MenuRightFinder[4488] ACTION performNewFile delegated UNAVAILABLE reason=peer verification failed
MenuRight[4571] MAIN-IPC peer REJECTED: SecStaticCodeCreateWithPath failed ... path=/Users/suxin/Applications/...
```

- `ExtensionIPCClient.expectedMainAppExecutablePath` 是**从扩展自己的 bundle 推导**的
  (`…/MenuRight.app/Contents/PlugIns/MenuRightFinder.appex` → `…/MenuRight.app`),主应用侧反向只认
  自己 bundle 里的那个 appex。这是**故意**的安全设计(同用户下谁都能 unlink socket 再自己 bind,
  所以必须钉死对端可执行文件路径),代价是:**扩展与主应用必须来自同一份 .app**。
- 当时机器上有 4 份副本都注册着同一个 bundle id(`~/Applications` 开发装、`/Applications` DMG 装、
  DerivedData Debug、`build/release-x86_64` Release),Finder 一直用**先注册的那份** `~/Applications`,
  而用户启动的是 `/Applications` 的那份 → 互相拒绝,所有委托操作失败。
- 处理:`xattr -dr com.apple.quarantine`(Chrome 下载的 DMG 装的带隔离属性)+
  `Scripts/prune-launchservices.sh /Applications/MenuRight.app`(注销 7 份陈旧注册,含 `/Volumes/MenuRight 1.0` 里那份)+
  重启应用。之后日志出现 `FINDER-IPC init IPC pong: ... from main-app PID=…`,说明握手通了。
- **`Scripts/prune-launchservices.sh` 的默认保留路径已改**:原来写死 `~/Applications/MenuRight.app`,
  在"DMG 装到 /Applications"的新现实下正好会留下错的那份。现在有 `/Applications/MenuRight.app`
  就用它,否则回退 `~/Applications`(`install-dev-app.sh` 一直显式传路径,不受影响)。
- **教训:Xcode 每次 build/test 都会把自己的产物注册进 LaunchServices**。跑完构建/测试要 `prune`,
  否则扩展可能又来自别的副本。这台机器验证过两次(每次 `xcodebuild test` 之后都多出两份)。

## 菜单栏图标(用户要的)

`MenuBarExtra`(.menu 样式)+ 三个纯数据层里的东西(可测):

- `MenuRight/App/StatusMenu/StatusMenuPlan.swift`:`StatusMenuCommand`(openSettings /
  checkForUpdates / quit)、`StatusMenuPlan.entries`(设置 / 检查更新 / ─── / 退出)、`StatusMenuIcon`、
  `StatusMenuUpdateOutcome.make(from: UpdateChecker.State)`。
- `MenuRight/App/StatusMenu/AppLifecycle.swift`:`terminatesAfterLastWindowClosed = false`。
  单独成文件是因为 **`MenuRightApp.swift` 持有 `@main`,测试 target 编不了它**;规则放这儿才能直接断言,
  再由源码级守卫检查 delegate 真的转发了它。
- `MenuRight/App/StatusMenu/StatusMenuView.swift`:菜单 UI + `StatusMenuLabel` + 两个 NSAlert。
- 新增 11 个单测(`StatusMenuTests`),含"贴了注释的源码守卫"(文件自己的文档注释就写着
  `applicationShouldTerminateAfterLastWindowClosed` 和 `MenuBarExtra`,不先剥注释等于没守卫)。

**生命周期**:Finder 扩展由 Finder 按需拉起、自己结束——没有任何 API 能让 App 启动/保活/结束它。
App 能做的是**自己别退**:扩展执行操作时要连主应用,主应用不在 → 每项都"主应用未运行"。
所以关窗口不再退出(`applicationShouldTerminateAfterLastWindowClosed` → false),菜单栏"退出"是唯一出口。

## 图标:SVG 是白的,必须 template;尺寸踩了两次

- `top-bar-logo.svg`(用户在仓库根目录给的)是 `fill="white"` 的两段路径 → 状态栏里**必须**用模板渲染
  (`template-rendering-intent: template`),否则白图标画在浅色菜单栏上等于看不见。放进
  `BrandAssets.xcassets/top-bar-logo.imageset/`;仓库根目录那份按既有约定进 `.gitignore`
  (设计原件不入库,库里的在 asset catalog)。
- **坑一**:SVG 内在尺寸 120pt → 状态栏被撑满、被菜单栏高度裁掉一大块(截图可见一个大白块)。
- **坑二**:`MenuBarExtra` 的 label **不吃 `.resizable().frame(width:height:)`**,改成明确交付一张
  已缩放的 `NSImage`(`image.size = 16×16` 且 `isTemplate = true`)才真的变正常。
  catalog 里的 SVG 也规范成 `width/height="16"`(保留 viewBox)。
- `check-icons.sh` 从"整个 catalog 必须/必须不是模板"改成"**同一 catalog 里可以只有一部分是模板**",
  并把状态栏图标(`assetName = "..."` 从 StatusMenuPlan.swift 抓)纳入检查。
