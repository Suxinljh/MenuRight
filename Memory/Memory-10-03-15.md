## 严重（High）

### H-1 加密 7z 的 scratch 整包落盘绕过自家 Zip Slip 守卫（已核验为真）
- 位置：`Shared/Archive/SevenZipPasswordSource.swift:175`
  `guard try decoder.extract(to: try Path(directory.path))`，由 `scratchDirectory()`（:166）调用，
  再由 `contents(of:)`（:137-138 `root.appendingPathComponent(member.name)`）触发。
- 机制：`decoder.extract(to:)` 是**整包**解压，PLzmaSDK 按条目原始路径落盘；
  App 的 `safeRelativePath`（`Shared/Archive/ArchiveExtractor.swift:103-137`）只在 plan 阶段
  （`ArchiveExtractor.swift:176-182`）把不安全条目记成 `.skipped(.unsafePath)`——
  但只要有**一个**安全条目要内容，整包（含 `../` 条目）就已经落到 scratch 目录之外。
  代码注释（`SevenZipPasswordSource.swift:96-107`）自称「members() 不解码，所以提取器的尺寸守卫与
  名字规则先跑；scratch 副本只会出现在 plan 通过之后」——该不变式被「SDK 调用是整包而非逐条目」破坏。
- 我读 PLzmaSDK 源码确认非推测：`build/DerivedData/SourcePackages/checkouts/PLzmaSDK/swift/Decoder.swift:140`
  `extract(to:itemsFullPath: Bool = true)` 默认拼条目路径；
  `.../PLzmaSDK/src/plzma_extract_callback.cpp` `ExtractCallback::getExtractStream`(:109 起) 用 kpidPath +
  `createDir(true)` + `fopen`；`.../PLzmaSDK/src/plzma_path_utils.hpp:426` `normalize()` 只折叠重复分隔符、
  映射附加分隔符、识别 `x://`，**完全不解析 `..`、不剥离前导分隔符**。
- 影响：条目 `../evil.txt` 写到 `<temp>/MenuRight-7z/<UUID>/../evil.txt`。App Sandbox 把它限制在
  应用自己容器的可写位置（`<container>/Data/...`，含自身偏好 plist）；非沙箱/放宽例外的变体＝任意写。
  同时 UI 把该条目报成「skipped (unsafe path)」，与实际落盘自相矛盾。
- 修法：不要用 `decoder.extract(to:)`，改用同文件已有的逐条目
  `SevenZipEncryption.decode(_:with:)`（`SevenZipPasswordSource.swift:145-155`；`extract(itemsToStreams:)`
  在 `:83` 已经在用），并在任何 SDK 调用前先跑 `safeRelativePath`。

### H-2 ZIP 解压炸弹：`rawInflate` 无输出上限
- 位置：`Shared/Archive/ZipReader.swift:295-326`；调用点 `:267`
  `Self.rawInflate(payload, expectedSize: entry.uncompressedSize)`。
- `:304` 只用 `expectedSize` 做 `reserveCapacity`（攻击者可控最多 4GiB 预分配），
  `:312-321` `repeat { ... output.append(...) } while status == Z_OK` 循环体内**没有任何 output.count 上限**，
  `expectedSize` 从不用于截断；尺寸校验在 `:278`、CRC 在 `:286`，都在整个 payload 驻留内存之后。
- planner 的预算（`ArchiveExtractor.swift:161-164`）也是对同一个「压缩包自报」字段求和。
- 修法：边解边比 `expectedSize`/限额，超限即抛 `.tooLarge`；不要信任中央目录里的 uncompressedSize。

### H-3 gzip/bzip2/xz 无上限解压，且「列名字」阶段就整体解压
- 位置：`Shared/Archive/ArchiveMemberSource.swift:251-263` payload 闭包 `Data(contentsOf:)` →
  `GzipArchive.unarchive` / `BZip2.decompress` / `XZArchive.unarchive` 整体物化；
  `:279` `guard let entries = try? TarContainer.info(container: try payload())` —— 对 tar.gz/tar.bz2/tar.xz
  仅为了列条目名就先整体解压，且发生在 plan 的限额判定之前；
  `declaredPayloadSize()` 对 bzip2/xz 返回 nil（`:309`），所以解压前只剩「文件大小」一道 guard。
- 修法：流式解压 + 限额；或先按「压缩比上限」拒绝，再解压。

### H-4 扩展侧 peer 校验 fail-open（设计缺陷，现实可利用性低）
- 位置：`Shared/IPC/PeerIdentity.swift:205-228`。`:212` 两个代码签名 API 都失败时，
  `:218` 只要 `expectedExecutablePath != nil`（扩展侧会传）就走 `:221-227`，
  仅凭 `executablePathsMatch`（`:258-260`，`URL(fileURLWithPath:).standardizedFileURL.path` 字符串比较）
  返回 `.verified(teamIdentifier: "unavailable")`，无签名/team/cdhash 校验。
  `:214-217` 注释自述这是 FinderSync appex 在沙箱下的**常态**（OSStatus 100001）。
  主应用走 `verify(fd:)`（`:245-251`）不传该参数，所以永远走 `:218` 的 reject。
- 可利用性：需在 0700 的 App Group 容器里抢占 `ipc.sock`（同用户非沙箱进程可以）
  **且**攻击者进程的内核报告路径恰等于 `MenuRight.app/Contents/MacOS/MenuRight`（等于已经能写应用包）。
- 修法：fail closed（拒绝）或改校验 cdhash/team；至少把 `teamIdentifier: "unavailable"` 当作未验证状态上报给 UI。

### H-5 模板目录 security-scoped bookmark 是死书签 —— 发布构建里自定义模板静默失效
