## 关键决策(全部有实测依据)

1. **钉 SWCompression 4.9.1,不用 develop**。4.9.1 的 manifest 是
   `swift-tools-version:5.9` + `platforms: [.macOS(.v14)]` + `swiftLanguageVersions: [.v5]`,
   与本项目完全一致;`develop` 是 tools 6.0 / macOS 15 / Swift 6,不可用。
   pbxproj 手写 `XCRemoteSwiftPackageReference`(kind = exactVersion) +
   两个 `XCSwiftPackageProductDependency`(app / 测试),`Package.resolved` 已落盘。
   —— 规划文档里 D2 的"5.9 + macOS 14"说的就是 4.9.1;**v4.0.0 是 tools 4.0 的老版本**,
   我一开始按 `from: 4.0.0` 解析到 4.9.1 才发现这点,已改成 exact 钉死。
2. **格式分工**: ZIP 继续用自研读写(它是我们也要写的格式,读侧按需 inflate、不整包解码,
   zip-slip 规则也是在它上面建立并测过的);TAR/7z/gz/bz2/xz 走库。压缩侧:
   ZIP = `ZipWriter`,TAR = `TarContainer.create`,TAR.GZ = `GzipArchive.archive`,
   TAR.BZ2 = `BZip2.compress`。**7z/xz 只能解不能压**(库无写能力)。
3. **统一成员模型**: 新增 `ArchiveMember` + `ArchiveMemberSource`,所有格式都先变成
   `[ArchiveMember]`(name / isDirectory / isSymbolicLink / uncompressedSize / isDecompressible),
   再喂给**同一个纯策略** `ArchiveExtractionPlanner`。安全规则因此只写一遍,覆盖所有格式。
   `members()` 保证不取负载,SIZE 守卫在写盘前跑;库的 `open`(整包解码)只在通过守卫后才调用。

## 实测踩到的坑(来自 subagent 的源码+实跑侦察,我逐条验证/采纳)

1. **TAR 目录名要自己加 `/`**:`TarContainer.create` 不会补,类型标志和尾斜杠都给才稳。
2. **py7zr / 7-Zip 默认会用 BCJ 过滤器**:`info` 能列出条目,`open` 抛
   `SevenZipError.compressionNotSupported`。所以 7z 的"不支持"必须映射成
   `unsupportedFormat` 的清晰文案,不能报"损坏"。
3. **TAR 的 magic 检测很弱**:`info`/`formatOf` 对空/全零输入不抛错,随机数据才抛
   `TarError.wrongField`。因此 `.tar` 分支用 `formatOf` 做有效性验证;空归档仍视为合法空包。
4. **加密 zip**:中央目录的通用标志位 bit 0 = 加密。我们在解析时就拒绝并给出
   "受密码保护、本版本不支持",而不是等到 CRC 失败。
5. 库没有 `isDirectory`,一切靠 `entry.info.type == .directory/.symbolicLink`。

   `RawZipBuilder` 自身的参数名(它也有 `entries:`),编译错误立刻暴露;教训是

3. 体积上限对 bzip2/xz 是"边解压边累计",因为库没有流式 API(整包 `Data`)。
   这一点没有藏起来,写进了 README 的残余风险段 —— 有边界就要写清楚边界。
