## B. ZIP 条目名编码(Windows 中文包乱码)

现象:`新建文件夹`(GBK 字节 `D0 C2 BD A8 CE C4 BC FE BC D0`,bit 11 **未设**)按 CP437 解出来是
`ÐÂ½¨ÎÄ¼þ¼Ð`——而且这个错误会落到**磁盘上的文件名**,不只是显示。

新增 `ZipNameDecoder`(`Shared/Archive/ZipReader.swift`),解码顺序:

1. bit 11 置位 → UTF-8(写入方撒谎时退回 lossy);
2. 纯 ASCII → ASCII;
3. 合法 UTF-8 → UTF-8(大量工具写 UTF-8 却不设标志位);
4. **以非 ASCII 为主**(高字节 ≥ 1/3)**且**是合法 GB18030 **且**结果真的含中日韩字符 → GB18030;
5. 否则 CP437(规范原文)。

不需要任何码表:CP437 = `kCFStringEncodingDOSLatinUS`,GB18030 = `GB_18030_2000`,
都在 Foundation 里。

**关键教训(第一版写错过)**:只用"能不能按 GB18030 解 + 含 CJK"当闸门**不够**——
GB18030 接受很大比例的字节对,于是 `Ünïc` 被解成 `歯媍`、`Übersicht.txt` 也会中招。
加"非 ASCII 字节占多数"这道闸门后就分开了:中文名几乎全是多字节;西文名是 ASCII 字母加一两个重音。
残留取舍:一个"以非 ASCII 为主 + 恰好合法 GB18030"的西文名仍会被读成中文,单测
`testMixedScriptCP437NameIsTheKnownCostOfPreferringChinese` **刻意钉住**这个行为,
免得后人朝"CP437 优先"的方向"修"回去——那会让每个 Windows 中文包乱码。

单测构造器 `RawZipBuilder` 拆出 `buildRaw(nameBytes:contents:externalAttributes:flags:)`,
原来的 `build(name:...)` 变成薄封装,原有用例不受影响。
