## 故障现象

`Scripts/install-dev-app.sh` 在第 1 步构建时失败：

```
Creating working copy of package ‘SWCompression’
Checking out 4.9.1 of package ‘SWCompression’
Couldn’t update repository submodules:
    Cloning into '.../SourcePackages/checkouts/SWCompression/Tests/Test Files'...
    fatal: Unable to read current working directory: No such file or directory
    fatal: fetch-pack: invalid index-pack output
xcodebuild: error: Could not resolve package dependencies: fatalError
```

## 根因（已取证）

**Xcode.app 与 `xcodebuild` 共用同一个默认 DerivedData**（`~/Library/Developer/Xcode/DerivedData/
<project>-<hash>`，两者 hash 相同）。两个 SwiftPM 进程同时对同一 `SourcePackages/checkouts` 做
首次 checkout 时，会互相删除/重建对方正在使用的工作副本；输的一方在
`git submodule update` 的 `index-pack` 子进程里 `getcwd()` 拿到 ENOENT，于是报
"Unable to read current working directory"。SWCompression 携带 `SWCompression-Test-Files`
子模块（路径 `Tests/Test Files`，含空格），是唯一会踩到这条路径的包。

证据：

1. `ls "$DD/Logs/Package"` 的 LogStoreManifest 显示同一 DerivedData 在 09:04:22、09:09:40、
   09:09:44 有三次 `Resolve Packages`；用户那次 CLI 构建在 09:09:36–09:09:42，失败信息就在
   8EF37E01 日志里（时间戳 812509782）。Xcode GUI（pid 503）当时正开着这个项目。
2. 用 `-derivedDataPath` 指向全新目录做**单进程**解析：4.5s 成功，子模块 159 个文件正常克隆 →
   网络/代理/子模块本身都没问题。
3. 人为让 3 个 `xcodebuild -resolvePackageDependencies` 指向同一个新 DerivedData 并并发执行：
   **三个全部失败**（`repository ... already exists unexpectedly` /
   `"info" couldn’t be copied ... already exists`）。SwiftPM 在同一 SourcePackages 上不是并发安全的。
4. 竞态目录 `rm -rf` 后**单独重试一次即成功**，说明"输的一方留下的是完整 checkout，重试可自愈"。
   这一点决定了修法。

## 修法（Scripts/install-dev-app.sh）

- 新增独立的第 1 步 `xcodebuild ... -resolvePackageDependencies`，**最多重试 3 次**（间隔 2s），
  失败时打印日志尾部并提示"Xcode 打开着就退出它 —— 两个 SwiftPM 进程不能共用一个 DerivedData"。
- 原来的构建步骤（现 2/7）加 `-disableAutomaticPackageResolution`，让 build 阶段不再回到
  checkout/submodule 路径；`-showBuildSettings` 同样加该参数。
- 步骤编号 1/6…6/6 顺延为 1/7…7/7；文件头 "WHY THIS SCRIPT EXISTS" 从两条坑扩为三条（新增第 3 条）。
- 子模块修复不需要改依赖、不需要删 DerivedData、不需要动 `Package.resolved`。
