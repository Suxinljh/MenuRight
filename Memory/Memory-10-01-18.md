`Scripts/release.sh` 从「只出两个 ZIP」扩成:dmg(hdiutil UDZO + 自检)+ zip + 源码 zip +
校验和,并把这些全挂到 `gh release create` 上。**发布说明的「构建与验证说明」是脚本生成的**,
不是手写:`uname -m` 决定哪个架构算「实测」,另一个一律写成**未经测试**——发布机只能执行自己的
架构,这句话不该由人记得写。

## 关键决策

- **Apple 版本必须在发布说明里明说未经测试**。本机是 Intel i9(x86_64),arm64 走交叉编译,
  只能做静态检查(lipo 架构、codesign 验签、DMG 挂载与包结构),**不能启动验证**。
  Rosetta 只能 arm64 机器跑 x86_64,反向不存在,所以这条无法在本机补上。
- **签字与公证的实话**:没有 Developer ID 证书,产物是 Apple Development + 内嵌
  *Mac Team Provisioning Profile*(`ProvisionedDevices` 只有本机 UUID,到期 2026-10-07)。
  因此这不是一个真正可分发给他人的构建,发布说明里写明了「若在别的 Mac 上因预置描述文件受限
  无法启动,请从源码构建」。要真分发,得申请 Developer ID + 公证,这是下一步的头等项。
- 发布是一次 `Scripts/release.sh --publish --notes <file>` 跑完:构建 → 打包 → 校验和 →
  建 tag → `git push origin v1.0` → `gh release create`(6 个资产)。`main` 另外单独 push。

## 坑

- **bash 3.2 会把多字节字符并进变量名**:`"发布机是 $HOST_ARCH,无法…"` 报
  `HOST_ARCH�: unbound variable`。macOS 的 `/bin/bash` 是 3.2,变量名解析不按 UTF-8 边界停,
  中文/全角字符紧跟变量时必须写 `${HOST_ARCH}`。已在脚本里留了注释。
  这个错只在 schema 走到最后才炸(构建完两个架构之后),所以必须用最小片段先验一遍。
- **`hdiutil verify` 的输出很吵**:校验和结论走 stderr、逐段进度走 stdout,脚本里要
  `>/dev/null 2>&1` 并自己判返回值,否则日志被 CRC 校验行淹没。
- **`Scripts/verify-archive-roundtrip.sh` 之前是坏的**(与本次发布无关的既有问题):harness 用
  符号链接把仓库源码拼成一个临时 SwiftPM 包,源码清单没跟上后来新增的
  `Shared/Archive/ArchiveOperationControl.swift` 与 `Shared/IPC/FileOperationContract.swift`,
  生成出来的包直接编译失败(bash 语法检查 `bash -n` 看不出来)。补上两个文件后 6 种格式往返 +
  恶意压缩包拒绝全部 PASS。**教训:凡是被 README 列为可复现验证的脚本,发版前要真跑一次。**
- 源码 zip 里带着仓库原有的 0 字节 `default.profraw`(历史遗留,已跟踪),本次没动它。

## 遗留 / 下一步

- **Developer ID 签名 + 公证**:不做的话,Release 里的包只有开发者自己的机器能用,
  「下载即用」这个承诺是空的(README 的「右键打开」只解决 Gatekeeper 警告,解决不了描述文件限制)。
- **arm64 必须在 Apple Silicon 机器上实测一次**(至少启动 + 空格预览扩展 + 右键菜单)。
- DMG 目前是「app + Applications 快捷方式」的朴素布局,没有背景图与图标定位;要做就得引入
  `create-dmg` 之类的做法或自己写 .DS_Store,本次刻意没上第三方依赖。
- 更新检查失败提示里没区分「GitHub 配额用尽」与「网络不通」;本轮实测的 403 说明配额是真会发生的。
