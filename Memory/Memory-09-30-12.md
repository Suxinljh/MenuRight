## 实现要点

1. **数据通路(不新增第二份状态)**:应用把整棵设置树以一个 JSON 写进 App Group `UserDefaults`
   (`SettingsStore.storageKey`);新增 `MenuRightFinder/FinderMenuLanguage.swift`,
   在**每次构建菜单**时读该 payload,只取语言字段。`UserDefaults` 是 cfprefsd 查询、不是文件扫描,
   菜单构建期"零文件 IO"的约束仍成立;**不做进程内缓存**,所以切换语言后下一次右键即生效。
   缺失/空/损坏/未知语言值一律回退 `.system` → 按系统首选语言解析(zh* → 简中,否则英文),
   与设置界面一致。
2. **文案统一到一份目录**:扩展 target 现在编译 `Shared/Settings/AppLanguage.swift` +
   `Localization.swift`,`NewFileKind` 也从该目录取名(与设置面板的 `NewFileType` 共用
   `newFileKind*` 文案,不会漂移)。仅在菜单措辞与设置行不同处新增 8 个 `finderMenu*` 键
   (创建别名/锁定/解锁/剪切/新建文件夹/粘贴到这里/复制文件夹名称/复制文件夹路径);
   子菜单标题用 `.categoryNewFile`。计划层改为携带 `StringKey`(不再烘焙英文字符串)。
3. **回放安全**:Finder 回放时 `representedObject` 过不了进程边界,扩展只能靠 `sender.title` 派发;
   `FinderMenuTitles` 因此提供**接受所有语言**的反查(`copySubject(forTitle:)`/`isUnlockTitle`/
   `newFileKind(forTitle:)`)。另外用测试断言"同一语言下所有动作标题互不相同",避免派发歧义。
4. **新增验证工具** `Scripts/preview-finder-menu.sh`:编译扩展自己的 plan/title 代码 + 读真实
   App Group plist,打印两种语言下的「背景右键菜单」和「选中文件菜单」,并对 8 组标题跑回放断言。
   → **文案/派发问题不用开 Finder 就能定位**,只有"Finder 是否真的画出来"仍需人工。

## 关键踩坑(都是我自己的假设错)

1. **payload 结构想错了**:我先按 `{"language":"zh-Hans"}` 顶层写解析和测试,测试全过 ——
   但读真实 plist 才发现实际是 `{"general":{"language":"zh-Hans","launchAtLogin":false}, ...}`,
   语言在 `general` 里。**我的测试只验证了我的假设,没有验证真实数据**。
   修正解析为 `general.language`,并把测试 payload 换成贴近真实编码的形状,另加一条
   "顶层 language 必须被忽略"的用例。教训:**共享存储的字段路径必须拿真实数据核对一次**。
2. **pbxproj 对象 ID 撞车**:我用了 `AASETR003`/`ABSETTST003` 作为新文件 ID,而这两个 ID 已被
   `MenuRightSettings.swift` 占用 → 同一个 ID 出现两次定义,文件被解析到错误的 group
   (`Shared/Settings/FinderMenuLanguage.swift`),构建报 "Build input file cannot be found"。
   修复:回退到本轮改动前,用 `fresh()` 先扫描候选 ID 是否存在再落笔,并加"全文件 ID 唯一性"自检。
   教训:**手工维护 pbxproj 时,ID 必须先在文件里查重**,不要凭前缀直觉命名。
3. 断言要精确(承接上一轮):`assert "separator" not in src` 会被 `joined(separator: "|")` 绊倒。
