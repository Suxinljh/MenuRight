## 严重（High）

- **H-1 加密 7z scratch 整包落盘** — `Shared/Archive/SevenZipPasswordSource.swift`：
  先判定布局再落盘。新增 `private enum Layout { case flat(directory: URL); case inMemory }` 与
  `decideLayout()`：只有「每一条非目录条目的名字都通过 `ArchiveExtractionPlanner.safeRelativePath`、
  叶子名 `leaf(of:)` 与安全名一致、且叶子（大小写不敏感）互不重复」时才用
  `decoder.extract(to:itemsFullPath: false)` 扁平落盘；否则该 archive 完全不调用 `extract(to:)`，
  逐条目 `SevenZipEncryption.decode(item, with:)` 在内存里解（`decodeInMemory`）。
  扁平布局安全的原因：`plzma_extract_callback.cpp:160` 在 `itemsFullPath == false` 时只用
  `itemPath.lastComponent()`，目录条目直接 return，所以不可能写出嵌套路径；叶子唯一性排除了
  「后一个条目 follow 前一个条目建的符号链接」。测试 3 个（恶意 `../escape.txt` 的归档必须不落盘、
  叶子重名归档走内存分支、普通嵌套名照常读出），旧代码会在 `<tmp>/MenuRight-7z/` 留下 escape.txt。
- **H-2 ZIP 解压炸弹** — A：`ZipReader.contents(of:password:maximumOutputBytes: Int64 = .max)`，
  `rawInflate(_:expectedSize:maximumBytes:)` 逐块先判后 append（`:362`），
  `reserveCapacity(min(max(expectedSize,0), 16MiB))` 挡住伪造头部触发的预分配；
  `ZipMemberSource` 把超限映射成 `ArchiveError.tooLarge`。Lead 负责的接线：
  `Shared/Archive/ArchiveExtractor.swift` 的 `maximumPayloadBytes: limit`（limit 仍来自设置里的 sizeLimitMB）
  + 两处穷尽 switch 补 `case .inflateExceedsLimit`。
- **H-3 gzip/bzip2/xz 无上限** — A：`ArchiveMemberSource` 新增 `BoundedGzip`（`inflateInit2_(&stream, 47, …)`
  流式限额）与 `XZIndex`（footer index 预判，解析失败必须回退到解压后查、绝不因解析失败拒包）；
  bzip2 无声明大小、SWCompression 无流式 API → 只能解压后查，残留风险写进代码注释与 `README.md:178`；
  `Data(contentsOf:options: [.mappedIfSafe])` + 读前 `checkFileSize()`；`members()` 的 `try?` 拆开，
  「读不了」区分成 `ArchiveError.readFailed`。新增 `PayloadCache`：tar.gz 不再每个成员重解压整包。
- **H-4 扩展侧 peer 校验 fail-open** — C：保留回退但显式化：`Verified.verificationLevel`
  （`.codeSignature` / `.executablePathOnly`）+ 纯可注入
  `executablePathOnlyDecision(expectedPath:peerPath:peerUID:peerGID:currentUID:currentGID:)`
  （两侧 `resolvingSymlinksInPath().standardizedFileURL` 后精确相等、uid/gid 必须一致），
  `.notice` 日志点名 appex 沙箱下 SecCode 返回 OSStatus 100001。**仍不拦**同 uid 替换预期路径文件
  （受限降级，主应用侧对扩展的签名校验未变）。
- **H-5 模板目录死书签** — Lead：`DocumentTemplateCatalog.overrideDirectory(for:)` 改为经
  `withOverrideDirectory(for:_:)`（`startAccessingSecurityScopedResource` + `defer stop`），
  新增 `resolveOverride(for:)`：书签优先、解析失败才回退路径字符串；`FileOperationDispatcher`
  删掉 `effectiveTemplateDirectory()`，改为 `withTemplateDirectory(of:_:)` 包住
  「模板在不在」检查与 `createFileFromTemplate` 的 `copyItem`。顺带修掉原来那条错误注释
  （旧注释声称 dispatcher 已持有该文件夹的 scoped access，其实持有的是目标目录的）。
  测试 3 个（书签与存储路径不一致时以书签为准、书签不可解析时回退路径且不报 broken、
  `withOverrideDirectory` 在目录不可用时完全不执行 body）。
- **H-6 设置读取与主线程写入的数据竞争** — Lead：`Shared/Settings/SettingsStore.swift` 去掉
  `@Published`，改手工 `objectWillChange.send()` + `NSLock` 保护的 `storage` + 任意线程可读的
  `var settings`；写仍只在主线程（`apply`），`reload()` 会 hop 主线程、只改内存并 `post` 通知

## 已知残留（本轮有意不改，写在这里以免被当成已修）

- **bzip2 无法在解压前限额**：SWCompression 没有流式 API，只能在解压后查大小；已写进代码注释与 README。
- **密码校验路径的 inflate 上限**：`ZipReader.validates(password:)`（`ArchivePasswordResolver` 用）
  调用 `contents(of:)` 时用默认 `.max`，所以恶意加密 ZIP 在「输入密码」阶段最多会膨胀到条目自报的
  uncompressedSize。改成头部 check byte 校验可以免掉这次膨胀，但会失去 CRC 级别的确认
  （1/256 误接受），本轮选择保留语义、如实记录。
- **同 uid 替换预期路径的二进制**：见 H-4。
- `landing/`（README + 96K 宣传页）的提交策略仍待用户决定，本轮不动。
