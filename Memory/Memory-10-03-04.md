## ② 7z 写入:PLzmaSDK(MIT)

- 用户三选一(m00746)后选了 **PLzmaSDK 1.4.2**(`https://github.com/OlehKulykov/PLzmaSDK.git`,MIT,
  基于 LZMA SDK 23.01,LZMA2,C++11 + C 绑定)。备选是系统 libarchive(BSD-2,不用新依赖,但要自带

- 代码:新文件 `Shared/Archive/SevenZipWriter.swift`(内存 `OutStream()` → `Encoder(fileType: .sevenZ,

  `copyContent()`);`ArchiveCompressor.writableFormats` 加 `.sevenZip`、`fileNameExtension` 返回 `"7z"`、

## ③ 自研 ZIP 加密:ZipCrypto

- 用户选了**只做 ZipCrypto**(兼容优先,不做 WinZip AES)。
- `Shared/FileOperations/ZipCrypto.swift`:12 字节加密头(前 10 随机 + CRC 高 16 位 + PKWARE 校验字节)、
  三键 keystream(`0x12345678/0x23456789/0x34567890`,CRC32 表 + `* 0x08088405 + 1`)、
  通用位 bit0 置位、版本需求 20、extra field 仍写 0。`ZipWriter.archive(…, encryption: ZipEncryption(password:))`。
- **外部实现验证**(关键):`/usr/bin/unzip -P <密码> -t` 能读我们写的;`/usr/bin/zip -e` 写的我们能读。
  纯自家互测没有意义。
- **踩到的坑**:Info-ZIP 的加密条目带 general-purpose **bit 3**(data descriptor),写头时还不知道 CRC,
  它把**该条目 DOS 时间戳的两字节**当校验值 —— 所以「Info-ZIP 的 checkByte ==(crc>>24)&0xFF」这个断言
  是错的(实测 98 ≠ 180)。我们自己的写入器先知道 CRC,写的是 PKWARE 规定的 CRC 高字节,并用
  「篡改自己档案的第 11 个密文字节 → unzip 报 incorrect password」来证明这个值真的被外部读者读取。
- **已知边界**:能**写**加密 zip,**读**还没做 —— `ZipReader` 见到 bit0 仍然抛 `encryptedNotSupported`,
  解压时报 `archive_unsupported`(「受密码保护、本版本还不能解」)。下一步:密码要进解压流程,
  而密码**不进 IPC 契约**(Finder 扩展永远拿不到密码),所以必须在主 App 内弹密码框。
