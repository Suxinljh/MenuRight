## 需求(用户给的稿)

像系统「已锁定的项目」提示:左上角**没有关闭,只有最小化**;左侧压缩包图标
(`/Users/suxin/Suxin/code/app/MenuRight/zip:7z.png`,236x222);中间一行**真实进度条**;
下面两个按钮:**暂停、取消**。

## 实现(四层)

1. **协议**:`IPCProtocol.Response.progress`(0…1)。**带 progress 的是中间帧,不带的是答复**;
   扩展端 `sendRequest` 改成循环读帧,一次请求可收多帧。控制走**新方法** `fileOperationControl`
   (payload `ArchiveControlRequest{clientRequestId, action}`),类型放在
   `FileOperationContract.swift`(app+appex+tests 都编),因为**两端都要用**;
   而 `ArchiveOperationControl` 只在 App 端(它 throw `ArchiveError`)。
2. **真实进度**:两段确定进度 —— 读取源文件(按字节,分母来自**只读元数据**的预扫描
   `ArchiveCompressor.sourceBytes(of:)`)+ 组装容器(按条目,来自 `ZipWriter` 的 deflate 循环,
   新增 `onEntry: ((Int) throws -> Void)?`)。
3. **暂停/取消**:`ArchiveOperationControl`(`checkpoint()` 每条目调用,暂停时 50ms 挂起;
   `report()` 汇报)+ `ArchiveOperationRegistry`(按 `clientRequestId` 路由)。
   控制消息走**独立连接**:数据连接正卡在等答复,控制帧插在那里要等它忙完才被读到。
   服务端 `connectionQueue` 本来就是并发,所以能立刻受理(不用改并发模型)。
4. **窗口**:`ArchiveProgressWindow`(appex),`styleMask: [.titled, .miniaturizable]`。

## 关键实测结论

- **`styleMask` 不带 `.closable` 时,AppKit 仍然画出关闭钮,但 `isEnabled == false`**
  (zoom 同理)。这正是设计稿的样子——所以窗口只要 `.titled` + `.miniaturizable`,
  不要试图去 hide 按钮。已写成断言:`testWindowOffersMinimizeAndNotClose`。
- **取消不是失败**:新增错误码 `cancelled_by_user`,扩展端 7 处失败分支全部静默
  (用户自己按的取消弹错误框是错的);且内存组装、取消后不留残档。
- 进度粒度**每条目**:单个超大文件只会在结束时跳一次 —— 已在代码注释与手册里写明。

## 工程文件事故(重要教训)

这轮把 `project.pbxproj` 弄坏两次,`xcodebuild` 直接报 "damaged … parse error":

1. 插入资源文件时锚点选成了 `files = ( );` 的**闭合括号之后**,条目落到了数组外面。
2. 后面用 `str.replace` 修的时候,子串匹配到了**第一次出现的位置**(定义区),
   把一条 `PBXFileReference` 定义插进了 `files = ( … )` **数组**里 —— 数组里放字典 = 语法错误。

**教训**:
- 往 pbxproj 插入条目,锚点必须包含足够上下文并落在正确的括号**内**;
- 用 `str.replace` 前先确认唯一性(`count(x) == 1`)并且**每次只替换第一处**时想清楚那一处在哪;
- 同一个文件跨 target 要**复用同一个 `PBXFileReference`**(像 ArchiveCompressor 那样),
  不要为一个文件建两个 ref——第二个 ref 不在任何 group 里,路径会解析到工程根目录;
- 每次改完 pbxproj 立刻 `plutil -lint`(它之前一直是可靠的判据),
  再用 `xcodebuild -list` 确认能解析。
