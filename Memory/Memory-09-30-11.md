## 结论与证据(全部来自逐行量测用户截图)

- 原生分隔符**有** 2px 细线:`y=68、138、352`(「新建文件夹/显示简介」「显示简介/显示」「查看显示选项/从 iPhone 导入」之间),
  跨度 x 88..309、meanLum≈0.90。
- 我们插入的 `.separator` 处**整行非白像素为 0**:`Copy Folder Path`(523..541)→ `New File`(620..637)
  间距 97px,而正常行距是 48px → 多出的正好是一个空槽(≈24pt)。
- 也就是说:`NSMenuItem.separator()` 和菜单图片**同源** —— Finder 在扩展菜单里保留槽位但不绘制,
  原生项由 Finder 自己画所以有细线。

## 教训 / 可复用

1. **"用户看到的怪异空白"要能定位到具体像素**:这次靠"原生分隔符有细线 vs 我们的位置整行全白"
   和"间距是正常行距的 2.02 倍"两条量测,直接把"空隙 = 被吃掉线的分隔符"钉死了,
   不需要猜也不需要反复试。
2. **同一个进程边界效应会连续咬人**:先咬图片(`Memory-09-30-09`),再咬分隔符。
   凡是从扩展交给 Finder 绘制的菜单元素,都要假设"只保留几何、不保留绘制语义"。
3. **断言要精确**:我一开始写 `assert "separator" not in src`,结果被 `joined(separator: "|")`
   里的诊断字符串绊倒,导致那次编辑没落盘,还先跑出了一个编译错误。
   断言"这个 case 没了我"要用 `case .separator`/`menu.addItem(.separator())` 这种精确串。

## 备选(未实施)

如果将来一定要在 Finder 菜单里看到一条**可见的分组线**,唯一可尝试的办法是插入一个
`isEnabled = false`、标题为连续制表线字符(如 `────`)的普通项 —— Finder 会按禁用文字色绘制它,
看起来像一条线(代价:仍占一个整行高度,且是 hack)。用户若要,再做并请其在 Finder 里确认。
