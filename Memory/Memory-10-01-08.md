## 需求与旧行为

「体积上限」原本只有 `Stepper`,`Text("\(sizeLimitMB) MB")` 只读;越过 `sizeLimitRange`
(1...8192)时 Stepper **静默拒绝** —— 到顶再点箭头什么都不发生,没有任何解释。
(顺带:「\(int)」走 `LocalizedStringKey` 插值,所以显示成带千分位的 `1,024 MB`。)

## 改法

1. **纯规则**:`ArchiveSettings.interpretSizeLimit(_:) -> SizeLimitEntry`
   (`Shared/Settings/ArchiveSettings.swift`,紧挨 `sizeLimitRange`,与解码的
   `normalized()` 共用同一个范围):
   - `.accepted(Int)` / `.aboveMaximum(stored:)` / `.belowMinimum(stored:)` / `.unusable`
   - 容忍 `1,024`、`1，024`、`1 024`、`1024 MB`、`1024mb`、首尾空格 —— 因为**行内常驻显示
     的就是 `1,024 MB`**,用户会选中它重打或粘回去。
   - 纯数字但超出 `Int` 位数 → 归 `.aboveMaximum`(比说"不是数字"正确)。
2. **UI**:`ArchiveSettingsView.sizeLimitGroup`
   - `TextField`(等宽、右对齐、宽 76)+「MB」+ Stepper;
   - 行常驻副标题 `可输入 1–8,192 MB`(最大値在输入前就可见),越界时替换为
     `最大不能超过 8,192 MB` / `最小不能小于 1 MB` / `请输入数字`;
   - `onChange(of: sizeLimitText)` 实时给提示(所以要**边打字边提示**,不是提交后才说);
   - 回车或失焦提交:越界存钳制值、无法解析回退到已存值,字段与设置不漂移;
   - 聚焦时编辑纯数字、失焦恢复千分位显示。
3. **本地化**:新增 `archiveSizeLimitRangeHint` / `MaxHint` / `MinHint` / `InvalidHint`
   (中英双语,`LocalizationTests` 自动校验占位符一致)。

## 顺带修:`MENURIGHT_REVIEW_WINDOW` 一直静默失效

这个 Debug review 钩子本来只在启动后 0.0s / 0.4s 各试一次,取
`NSApp.windows.first(where: { $0.isVisible })`。实测:SwiftUI 窗口在这两个时刻
**`isVisible == false`**(虽然窗口已经存在),于是两次都跳过,请求 1100x1180 结果窗口还是 960x692,
而且**毫无反馈**。现在:优先可见窗口、否则退化为 `NSApp.windows.first`,最多坚持 5 秒,
成功时 `NSLog("[MenuRight] review window sized to … after N attempt(s)")`。
实测通过:`review window sized to {1100, 1180} after 2 attempt(s)`。

**教训**:非激活窗口里 macOS 26 的 `Toggle` 会渲染成"关"的样子(灰色胶囊、滑块在左),
我一度以为格式开关全没生效;`open -a` 激活后重截就是全开紫色。**看截图前先让窗口成为 key window。**

## 清理

`MENURIGHT_SELFTEST_SETTINGS=write` 会把 `sizeLimitMB` 写成
`Int(Date().timeIntervalSince1970) % 8000 + 1` —— 用户截图里的 `1,038 MB` 就是这么来的
(先前跑自检没 reset,是我的遗留)。已用 `MENURIGHT_SELFTEST_SETTINGS=reset` 恢复为默认 1024,
并确认 6 种格式仍在启用。**以后跑 write 自检必须跟着 reset。**
