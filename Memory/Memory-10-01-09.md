## 现象与取证

用户:主程序在运行,选文件夹 → 压缩 → 压缩为 ZIP → 弹「MenuRight 未运行」(详情 `read failed`),
**数秒后压缩包却真的出现了**,而且全程没有任何进度提示。

日志精确到秒:

```
03:22:52 finder-sync request kind=compressItems
03:22:52 main-app    收到请求
03:22:57 finder-sync read failed        ← 整整 5 秒
03:23:06 finder-sync 再试一次(用户重试 → 又压了一次)
03:23:11 finder-sync read failed        ← 又是 5 秒
```

## 根因

文件操作是**一次性请求/响应**:主程序要压完才回包。而传输层的通用帧上限是
`UnixSocketTransport.defaultTimeoutSeconds = 5`,扩展等 5 秒就放弃。

致命之处在于 `readFrame` 只返回 `Data?` —— **超时和对端断开被合并成同一个 nil**,
于是"对端还在干活"被渲染成"对端不在",UI 还叫用户去打开主程序、重试
(而重试会再压一次,正是日志里 03:23:06 那次)。

## 修法(四层)

1. `UnixSocketTransport.FrameReadResult`(`.frame/.timedOut/.closed/.failed`) +
   `readFrameResult` 保留失败原因;`readFrame` 保持 `Data?` 兼容旧调用。
2. `MenuRightIPC.fileOperationTimeoutSeconds = 600`,两端共用;文件操作走长预算。
3. `ExtensionIPCClient.FileOperationOutcome` 新增 `.stillRunning`;
   `FinderSync` 7 处 outcome 分支都处理它,文案「操作仍在进行」并**明确不要重复操作**。
4. **进度提示**:`sendDelegated` 是所有文件操作的唯一漏斗(`ipcQueue.async` 全项目只有两处),
   在这里挂浮层:1.5 秒后才出现(快操作不闪窗)、出结果即撤下、只有「隐藏」按钮
   (点了只收起、不打断)。带 `delegatedToken` 防串台(第二次点击不会盖掉第一次的提示,
   第一次结束也不会撤掉第二次的)。

## 差点漏掉的坑(重要)

socket 上还设了 5 秒 `SO_RCVTIMEO`。若读返回 `EAGAIN` 就直接判失败,那 600 秒上限**根本用不上**
—— bug 会原样复现。已改成 EAGAIN/EWOULDBLOCK 继续等(带 10ms 小睡防自旋),由调用方 deadline 决断。
测试 `testQuietPeerIsWaitedOutPastTheSocketReceiveTimeout`(把 SO_RCVTIMEO 调到 0.2s、
0.8s 后才发帧)守住它。

## 探针发现的两个 AppKit 陷阱

- `NSAlert` 在**不加任何按钮**时会**自动补一个英文 "OK"**(`buttons.count == 1`)。
  想要"无按钮"是做不到的,得显式 `addButton` 并自己命名/接 action。
- `accessoryView` 不显式设 `frame` 会被布局成 `{0,0}`,转圈看不见。
- `layout()` 依旧必要:不加它,面板会露出「不再显示此信息」勾选框与空按钮槽(同 10-01-06 的结论)。
