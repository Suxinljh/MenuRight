## 2. P7-b 常用三项

- `MenuRightFinder/FinderFavorites.swift`(新,扩展 + 测试):**独立的极小解码器**,只读
  `favoriteFolders/favoriteApps/favoriteWebsites`。刻意不复用 App 的 settings 模型:appex 不该
  把整个设置树和 `decodeOr` 拖进沙箱扩展。禁用行丢弃、空行跳过、网址必须 http(s)+host、
  软件没有 path 时回退 bundle id。
- **标题必须唯一**:Finder 回放只给标题(`representedObject` 不过进程边界),同名条目会互相顶替。
  规则:重名 → 追加来源后缀(`GitHub — github.com`),仍冲突再 `(2)`;纯函数,故菜单构建与点击
  时重新推导得到同一组标题。
- 菜单:`FinderMenuBuilder.plan` 末尾按规格顺序追加 **常用软件 ▸ / 常用网页 ▸ / 常用文件夹 ▸**,
  空列表不出现;**选中态菜单仍是平铺**(常用项只属于"在哪个文件夹右键")。
- 线上契约(纯增量):`openFolder` / `openApplication` / `openURL` + `OperationArgs.target`
  (错误码复用已有的 `openFailed`)。
- 主 App 执行打开,**不加授权门**(与 `openTerminal` 同理:主 App 不读写目标,Finder/LaunchServices 代劳;
  加门会让未授权目录里的常用项全部失效)。只校验形状:存在的目录、绝对路径或 bundle id、http(s) URL。
  软件是否存在在**点击时**才查(菜单构建禁止 IO)。
- `OperationPresenter.presentDelegatedOpenFailure` 弹 "Couldn't open “标题”" + 服务端给的具体原因。

## 3. Spike S6(本轮最重要的实测结论)

`SystemOpener` 原记录:沙箱里 `NSWorkspace.open(_:withApplicationAt:)`(指名启动某 app)被拒
(`permErr -54`),所以 Open Terminal 只能走 Terminal 的 Finder 服务。常用项需要的是
**默认处理程序路线**,于是我在签名+沙箱的真 App 里量了四种目标:

| 目标 | 结果 | 观察到的副作用 |
| --- | --- | --- |
| `folder:/tmp/menuright-spike` | SUCCESS | Finder 真的打开了该目录 |
| `url:https://example.com` | SUCCESS | 默认浏览器打开链接 |
| `app:/System/Applications/TextEdit.app` | SUCCESS | TextEdit 真的启动了(事后已退出) |
| `bundle:com.apple.TextEdit` | SUCCESS | 同上,由 bundle id 解析 |

→ **允许的是 `NSWorkspace.open(_:configuration:)`;被拒的只有"指名应用"那条。**
复现:`MENURIGHT_SELFTEST_OPEN_TARGET=folder:/tmp/x .../MenuRight.app/Contents/MacOS/MenuRight`
(`url:` / `app:` / `bundle:` 同理)。这个 DEBUG 钩子留在代码里当回归手段。

## 复盘要点

1. 又一次"结构上都能跑、结果不对"的反面:如果按老结论(沙箱不能启动 app)直接砍掉常用软件,
   功能就白丢一半。**先量再做**,并把量法留成可复现的钩子。
2. `activateFileViewerSelecting` 返回 `Void` 不是 `Bool`(编译期才发现),打开文件夹的兜底因此
   改为"打不开窗口就 reveal",不再假装能判断成败。
3. `SystemOpener` 从 1 个闭包变成 4 个 ⇒ 必须改显式 `init`(不给默认空实现,避免"默认静默成功"),
   测试里的注入点随之更新(记录了 folder/url/app 三个新数组)。
4. 标题唯一性是**回放协议的硬约束**,不是 UI 细节:两个同名收藏点谁都可能开错。
