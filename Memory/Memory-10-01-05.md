## 现象与取证

用户:点「解压到当前文件夹」→ 无任何反应 → 右键里 MenuRight 条目**整个消失** → 过一会才回来。

诊断日志(10:21:48 / 10:24:16 两次点击):

```
02:23:55 ext(19489)  extension: connect failed: connect() failed: No such file or directory
02:24:16 ext(19489)  file operation request … kind=extractArchive
02:24:16 ext(19489)  file operation unavailable: connect() failed: No such file or directory
02:25:10 main(19974) MenuRightApp.init          ← 主 App 这时才起
02:25:16 ext(19978)  file operation batch success count=1
```

**主 App 那 18 分钟没在运行**,socket 文件不存在,所以点击必然走
`presentMainAppUnavailable` → `OperationPresenter.presentTitle` → `NSAlert.runModal()`。

## 根因

`runModal()` 在**扩展主线程**上开嵌套消息循环,而 Finder 调 `menu(for:)` 用的就是这条线程。
提示框一旦被压在别的窗口后面,主线程就无限期停在那里 —— 期间 Finder 拿不到菜单,
**MenuRight 条目静默消失**;等用户点到框、或 Finder 把扩展替换掉,菜单才回来。

这就是 `FinderSync.swift:36-42` 注释里写的那类 bug(项目当年为此把 IPC 挪到 `ipcQueue`),
**提示框是同类里最后一条漏网的**:全扩展只有这一处 `runModal`。

顺带排除:`MenuRightFinder` 全部源码 grep `runModal|.wait(|sleep(|.sync|semaphore` 只有它一处;
菜单构建实测 **4ms**(10:25:12.380 → 12.384),所以和上轮加的图标 IO 无关。

## 修法

`Shared/FileOperations/OperationPresenter.swift`:`presentTitleOnMain` 不再 `runModal()`:

- alert 自己的窗口 `makeKeyAndOrderFront` + `level = .floating` + `canJoinAllSpaces`;
- OK 按钮挂自己的 action(`AlertDismisser`)——非模态下 NSAlert 内置按钮会去调 `stopModal`,是 no-op;
- 同一时刻只保留一个提示;20 秒自动 `orderOut`,不会堆积;
- `NSApp?` 可选(测试进程里没有 NSApplication)。

所有失败入口(`presentMainAppUnavailable` / `presentDelegatedItemFailures` /
`presentDelegatedArchiveFailure` / `presentFolderAccessRequired` / …)都走 `presentTitle`,
所以一处修完全覆盖。
