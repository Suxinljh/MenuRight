## 关键结论(本地 SDK 实测,非推测)

- **Finder 扩展只能提供一个由 Finder 挂在扩展名条目下的 NSMenu**(`FinderSync.h:144-165`),
  无法创建顶层项、无法控制父级 → 需求中的"与 MenuRight 同级"**平台层面不可实现**。
  替代方案只有 Accessibility/AppleScript 注入菜单,被 `AGENTS.md:10` 禁止。
- **"新建后进入重命名/编辑态"没有 API**(Finder 只对自己创建的项目进入内联重命名);
  `NSWorkspace` 只有 `activateFileViewerSelectingURLs`(NSWorkspace.h:53)。
- **Finder 上下文菜单不响应快捷键** → P2 快捷键只能做全局热键,且拿不到当前选中项。
- 可行性确认:`NSURL.writeBookmarkData:toURL:options:` + `NSURLBookmarkCreationSuitableForBookmarkFile`
  (NSURL.h:427/459)= 真正的 Finder 别名;`NSFileImmutable`(NSFileManager.h:595)= `UF_IMMUTABLE`;
  `NSWorkspace.openURLs:withApplicationAtURL:configuration:`(NSWorkspace.h:43)用于打开终端;
  Quick Look 代码预览是受支持的扩展点(`com.apple.quicklook.preview` + `QLPreviewingController`,
  Xcode 自带模板)。
- **归档关键发现**:`import zlib` 在 Swift 中可用且 `inflateInit` 返回 `Z_OK`(zlib 1.2.12,
  `usr/include/zlib.h` 在 SDK 中)→ ZIP 解压可零第三方依赖自研;`bzlib.h` 公开但 **`lzma.h` 不在 SDK**;
  `libarchive` 在 SDK 中只有 `.tbd` **没有头文件** → 用它需手写声明,违背"仅公开 API"原则(不建议)。

## 依赖实测(源码已下载校验,非记忆)

选中 **SWCompression**(`/tmp/swc-src`,master tarball):
- MIT 许可;纯 Swift;`swift-tools-version:5.9`;`platforms: [.macOS(.v14)]`(与项目 deployment target 完全一致);自带 `PrivacyInfo.xcprivacy`。
- 能力:**ZIP 只读**(`ZipContainer.open/info`)、**7-Zip 只读**(`7zContainer.open/info`)、**TAR 读写**(`TarContainer.create/open`)、
  GZip/XZ/Zlib 解压(`unarchive`)、BZip2/LZ4/Deflate 压缩+解压、LZMA/LZMA2 解压。
- **不支持 RAR**(全库无 RAR API)。
- **不支持 ZIP 写入** → D1 的 OOXML 生成需要额外的 ZIP 写入器。
- 内存模型:入参为 `Data`(整包进内存)→ 必须加体积上限守卫,否则大压缩包会 OOM。

其它候选核实:UnrarKit = Objective-C、只读 RAR、基于 UnRAR 5.8.1(2018)、**不支持 SwiftPM**(仅 CocoaPods/Carthage);
libarchive 在 SDK 中只有 `.tbd` 无头文件。

## 排障:应用界面一直显示 "Finder Extension: Disabled"(2026-09-30 下午)

**症状**:Xcode 重新构建并启动 App 后,窗口始终显示 Disabled;用户怀疑拿不到权限。
实际 Folder Access 已 Authorized,所以与沙箱/书签无关。

**两个各自独立的真实原因**(都实测确认):

1. **`cp -R` 复制 Xcode 构建的 .app 会产出"签名看似有效但被内核杀死"的副本。**
   - 崩溃报告 `~/Library/Logs/DiagnosticReports/MenuRight-*.ips`:
     `signal=SIGKILL (Code Signature Invalid)`,`namespace=CODESIGNING`,`indicator=Taskgated Invalid Signature`。
   - `codesign --verify --deep --strict` 对 `cp -R` 副本仍报 "valid on disk",**查不出来**。
   - A/B 实测(同一个构建):从 DerivedData 直接运行 = ALIVE;`ditto` 复制到别处 = ALIVE;
     `cp -R` 复制到 ~/Applications = **必被杀死**。原因是 Debug 构建的调试 dylib 依赖硬链接,
     `cp -R` 会解开它们。**结论:复制 .app 只能用 `ditto`。**
   - 另外,8/30 那份旧副本的 provisioning profile 已于 **2026-09-06 过期**;Personal Team 的
     profile 只有 7 天有效期,过期后同样被 taskgated 拒绝。重新 `-allowProvisioningUpdates` 构建即换新。

2. **`FIFinderSyncController.isExtensionEnabled` 回答的是"系统已注册并启用的那一份",不是"你正在运行的那一份"。**
   - 实测(同一个二进制,仅路径不同):从 `~/Applications/MenuRight.app` 运行 → `true`;
     从 DerivedData 运行(Xcode Run)→ `false`。已写入诊断日志 `extension status isExtensionEnabled=...`。
   - 所以只要系统里存在两份副本,从 Xcode 运行就会显示 Disabled,
     而 Finder 实际加载的是已注册那份的扩展 —— 可能正是**旧代码**,这是最危险的陷阱。

**交付的修复**:
- `Scripts/install-dev-app.sh`:签名构建 → 校验产物签名 → **ditto 安装** → 验证安装副本能启动 →
  `lsregister` + `pluginkit -a` + `pluginkit -e use` → 打印系统状态。已在真机跑通。
- `ContentView` 现在显示**正在运行副本的 bundle 路径**,并在 Disabled 时给出"你运行的不是已启用的那一份"的提示,
  同时把状态写进诊断日志(把隐形陷阱变成可见信息)。
- 清理:`~/Applications` 下多余的旧副本(含 `cp -R` 坏副本、过期 profile 副本)已移到 `~/MenuRight-old-copies/`,
  只保留一份(未删除,用户可自行清理)。

**给下一次会话的规则**:改完扩展后必须 ①用脚本安装(ditto)②只保留一份副本 ③用 `pluginkit -m -i <id> -v`
确认 `+` 且路径正确 ④再用诊断日志里的 `extension status` 交叉验证界面状态。

## 排障 2:"右键菜单不显示" + "Open Terminal 无效"(2026-09-30 傍晚)

**A. 菜单不显示** —— 与权限无关。日志证据:
- 14:47:55 扩展**确实**构建出菜单(`menu(for:) kind=1`、`plan.count=8`、`returning menu with 8 items`),用户也看到过;
- 14:48 之后 Finder **再也没有调用过** `menu(for:)`;
- `pluginkit -m -p com.apple.FinderSync` 里 **MenuRight 整个消失了**(只剩百度/快压/WPS)。
原因:替换 .app 会让 .appex 拿到**新的 plugin identity**,而 Finder 一直用它缓存的插件列表。
`pluginkit -e use` 不够,必须 **`killall Finder`**。已加进 `Scripts/install-dev-app.sh`,并在脚本里改为
"轮询 `pluginkit -m -p com.apple.FinderSync` 直到出现且为 `+`"再报成功。

**B. Open Terminal 无效** —— 请求根本没离开扩展。日志:
`FINDER-IPC peer REJECTED: SecStaticCodeCreateWithPath failed OSStatus=100001`。
**关键实测结论:沙箱化的 appex 完全无法对"对端"使用 code-signing API**
(`SecCodeCopyGuestWithAttributes` 与 `SecStaticCodeCreateWithPath` 都返回 100001),
而**同一个**调用在主 App 里完全正常(`MAIN-IPC peer OK ... team=92X76S5UFL`)。
`proc_pidpath_audittoken` 在扩展里**可用**,内核给出真实路径 → 这是沙箱内唯一可用的强校验。

**修复(分层)**:
1. 主校验仍是 audit token → live SecCode → requirement(主 App 侧照旧,未削弱)。
2. live 不可用 → 静态签名校验(在能用 code-signing API 的环境仍然生效;且"校验过但不过"一律拒绝,不降级)。
3. 两条签名 API 都不可用(本机沙箱现状)→ 用**内核报告的 peer 可执行路径**做精确比对
   (期望值由自身 bundle 推导:`containingAppBundleURL` + 常规布局),并**每次记录降级警告**;
   没有期望路径时一律拒绝(不fail-open)。
   - 这样"unlink socket 后自行 bind"的攻击者必须运行**我们安装的那份可执行文件**才可能通过,
     除非他能改写我们的 app bundle。
   - 踩到的坑:`Bundle.main.bundleURL` 带**尾部斜杠**,三次 `deletingLastPathComponent()` 会多退一级
     导致派生值为 nil(等于静默关闭校验);另外扩展沙箱内 `Bundle(url:)` 读不到主 App 的 Info.plist,
     所以加了 `conventionalExecutablePath`(`<App>.app/Contents/MacOS/<App>`)兜底。两处都有单测。

**验证**:扩展启动日志从 `init IPC unavailable: peer verification failed` 变为
`init IPC pong: pong(=hello-from-ext …, from main-app PID=…)` —— IPC 往返打通。
测试数 184 → 188。

**仍待验证**:`Open Terminal` 在主 App(沙箱)里能否真的让 Terminal 以指定目录开窗(Spike S1)。
现在请求能到达主 App 了,若失败日志会出现 `DISPATCH openTerminal FAILED … error=…`。

## 排障 3:重启竞争 + Open Terminal 真实原因(2026-09-30 傍晚)

**C. 点击 Open Terminal 无反应、之后菜单消失** —— 不是菜单问题,是**主 App 根本没在监听**。
日志按时间顺序:
```
15:11:08  35096(新实例): start(): another listener is already running     ← 旧实例 34473 仍持有 socket
15:11:15  34473(旧实例): listener stopped + 取消链接
15:11:19  35125(扩展):   connect failed: No such file or directory          ← 新实例永久放弃 → 无人监听
```
原因:`startLocked()` 一次 bind 失败就**永久放弃**。重启 App 时旧实例还没退干净是常态,于是新实例永远不可达。
**修复**:bind 遇到"已有监听者"改为**带退避重试**(0.5s × 60 次),成功的日志会写 `listening after N retry/retries`;
`stop()` 会让待重试的循环停下;`applicationDidBecomeActive` 在预算耗尽后重新武装(自愈)。
踩到的坑:`MenuRightApp.swift` 在 willFinishLaunching 和 didFinishLaunching **各调用一次 `start()`**,
于是出现两条并发重试链,尝试次数翻倍(实测恰好在第 60/60 次才成功)。已加 `bindRetryScheduled` 保证单链。

**D. 顺带修复可观测性**:
- 窗口新增 "File Operations" 行显示主 App IPC 状态(Listening / Waiting for the previous instance /
  Failed),把"App 没在服务"从一个只能翻日志的现象变成一眼可见。
- `OperationPresenter.presentTitle` 现在自己切到主线程,不再依赖调用方记得切。

**E. Spike S1 结论(实测,不再是猜测):App Sandbox 里无法直接启动别的 App。**
```
DISPATCH openTerminal FAILED error=NSCocoaErrorDomain Code=256
  UserInfo={NSURL=file:///System/Applications/Utilities/Terminal.app/,
            NSUnderlyingError=NSOSStatusErrorDomain Code=-54 "permErr: permissions error (on file open)"
            _LSFunction=_LSOpenStuffCallLocal}
```
`NSWorkspace.open(_:withApplicationAt:)` 被沙箱拒绝。**可用方案:Terminal 的 Finder 服务
"New Terminal at Folder"** —— 通过 `NSPerformService(name, privatePasteboard)` 交给 Services 基础设施执行,
实际动作发生在 Terminal 自己进程里(不受我们沙箱限制)。
实测:`NSPerformService("New Terminal at Folder", pb)` 返回 true(中文标题返回 false,英文默认标题在中文系统上同样有效),
且**新 shell 的 cwd 正是目标目录**(父进程链 Terminal.app → login → -zsh)。已改为
`SystemOpener` 服务优先、直接启动作兜底,并把 permErr 隐藏在我们的错误信息之外。

**新增调试钩子(Debug only)**:`MENURIGHT_SELFTEST_OPEN_TERMINAL=/some/dir <app>/Contents/MacOS/MenuRight`
会用**真实沙箱 + 真实 dispatcher 路径**跑一次 openTerminal 并写日志后退出,不需要签名扩展就能验证沙箱行为。

**测试**:188 → 190(新增两个重启竞争回归测试:第二个实例必须在第一个退出后接管;
被 stop 的实例不得在之后偷绑)。
