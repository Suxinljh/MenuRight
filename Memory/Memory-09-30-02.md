## 关键结论(本地 SDK 实测,非推测)

- **Finder 扩展只能提供一个由 Finder 挂在扩展名条目下的 NSMenu**(`FinderSync.h:144-165`),
  无法创建顶层项、无法控制父级 → 需求中的"与 MenuRight 同级"**平台层面不可实现**。
  替代方案只有 Accessibility/AppleScript 注入菜单,被 `AGENTS.md:10` 禁止。
- **"新建后进入重命名/编辑态"没有 API**(Finder 只对自己创建的项目进入内联重命名);
  `NSWorkspace` 只有 `activateFileViewerSelectingURLs`(NSWorkspace.h:53)。
- **Finder 上下文菜单不响应快捷键** → P2 快捷键只能做全局热键,且拿不到当前选中项。
- 可行性确认:`NSURL.writeBookmarkData:toURL:options:` + `NSURLBookmarkCreationSuitableForBookmarkFile`
  (NSURL.h:427/459)= 真正的 Finder 别名;`NSFileImmutable`(NSFileManager.h:595)= `UF_IMMUTABLE`;
  `NSWorkspace.openURLs:withApplicationAtURL:configuration:`(NSWorkspace.h:43)用于打开终端;
  Quick Look 代码预览是受支持的扩展点(`com.apple.quicklook.preview` + `QLPreviewingController`,
  Xcode 自带模板)。
- **归档关键发现**:`import zlib` 在 Swift 中可用且 `inflateInit` 返回 `Z_OK`(zlib 1.2.12,
  `usr/include/zlib.h` 在 SDK 中)→ ZIP 解压可零第三方依赖自研;`bzlib.h` 公开但 **`lzma.h` 不在 SDK**;
  `libarchive` 在 SDK 中只有 `.tbd` **没有头文件** → 用它需手写声明,违背"仅公开 API"原则(不建议)。

## 依赖实测(源码已下载校验,非记忆)

选中 **SWCompression**(`/tmp/swc-src`,master tarball):
- MIT 许可;纯 Swift;`swift-tools-version:5.9`;`platforms: [.macOS(.v14)]`(与项目 deployment target 完全一致);自带 `PrivacyInfo.xcprivacy`。
- 能力:**ZIP 只读**(`ZipContainer.open/info`)、**7-Zip 只读**(`7zContainer.open/info`)、**TAR 读写**(`TarContainer.create/open`)、
  GZip/XZ/Zlib 解压(`unarchive`)、BZip2/LZ4/Deflate 压缩+解压、LZMA/LZMA2 解压。
- **不支持 RAR**(全库无 RAR API)。
- **不支持 ZIP 写入** → D1 的 OOXML 生成需要额外的 ZIP 写入器。
- 内存模型:入参为 `Data`(整包进内存)→ 必须加体积上限守卫,否则大压缩包会 OOM。

其它候选核实:UnrarKit = Objective-C、只读 RAR、基于 UnRAR 5.8.1(2018)、**不支持 SwiftPM**(仅 CocoaPods/Carthage);
libarchive 在 SDK 中只有 `.tbd` 无头文件。

## 排障:应用界面一直显示 "Finder Extension: Disabled"(2026-09-30 下午)

**症状**:Xcode 重新构建并启动 App 后,窗口始终显示 Disabled;用户怀疑拿不到权限。
实际 Folder Access 已 Authorized,所以与沙箱/书签无关。

**两个各自独立的真实原因**(都实测确认):

1. **`cp -R` 复制 Xcode 构建的 .app 会产出"签名看似有效但被内核杀死"的副本。**
   - 崩溃报告 `~/Library/Logs/DiagnosticReports/MenuRight-*.ips`:
     `signal=SIGKILL (Code Signature Invalid)`,`namespace=CODESIGNING`,`indicator=Taskgated Invalid Signature`。
   - `codesign --verify --deep --strict` 对 `cp -R` 副本仍报 "valid on disk",**查不出来**。
   - A/B 实测(同一个构建):从 DerivedData 直接运行 = ALIVE;`ditto` 复制到别处 = ALIVE;
     `cp -R` 复制到 ~/Applications = **必被杀死**。原因是 Debug 构建的调试 dylib 依赖硬链接,
     `cp -R` 会解开它们。**结论:复制 .app 只能用 `ditto`。**
   - 另外,8/30 那份旧副本的 provisioning profile 已于 **2026-09-06 过期**;Personal Team 的
     profile 只有 7 天有效期,过期后同样被 taskgated 拒绝。重新 `-allowProvisioningUpdates` 构建即换新。

2. **`FIFinderSyncController.isExtensionEnabled` 回答的是"系统已注册并启用的那一份",不是"你正在运行的那一份"。**
   - 实测(同一个二进制,仅路径不同):从 `~/Applications/MenuRight.app` 运行 → `true`;
     从 DerivedData 运行(Xcode Run)→ `false`。已写入诊断日志 `extension status isExtensionEnabled=...`。
   - 所以只要系统里存在两份副本,从 Xcode 运行就会显示 Disabled,
     而 Finder 实际加载的是已注册那份的扩展 —— 可能正是**旧代码**,这是最危险的陷阱。

**交付的修复**:
- `Scripts/install-dev-app.sh`:签名构建 → 校验产物签名 → **ditto 安装** → 验证安装副本能启动 →
  `lsregister` + `pluginkit -a` + `pluginkit -e use` → 打印系统状态。已在真机跑通。
- `ContentView` 现在显示**正在运行副本的 bundle 路径**,并在 Disabled 时给出"你运行的不是已启用的那一份"的提示,
  同时把状态写进诊断日志(把隐形陷阱变成可见信息)。
- 清理:`~/Applications` 下多余的旧副本(含 `cp -R` 坏副本、过期 profile 副本)已移到 `~/MenuRight-old-copies/`,
  只保留一份(未删除,用户可自行清理)。
