用户报「**加密压缩失败**」(m01529 截图 + m01530 三个字)。这不是加密的问题,是**自定义压缩对话框写盘
时没有 security-scoped access**。已修 + 真沙箱端到端取证。

## 现象与根因

- 用户截图:格式 ZIP、勾选「加密压缩」并输入密码、位置 `/Users/suxin/Downloads/webp_images`,点「确定」后红字
  `压缩失败: Could not read the archive: “mr-代码主题.webp” could not be read: The file “mr-代码主题.webp” couldn't be opened because you don't have permission to view it.`
- 根因:`Shared/FileOperations/FileOperationDispatcher.swift` 的 `handleCompressItems` 里,
  **customize 分支只把请求停在 `ArchiveRequestCenter` 上就 `return .success(createdPath: nil)`**,
  没有 `withAuthorizations`;同步分支才在 `withAuthorizations` 里写盘。用户按「确定」距 `dispatch`
  已过去几分钟,那次 security-scoped access 早停了 → 沙箱拒绝读源文件 → 抛 `ArchiveError.readFailed`。
- **与加密无关**:不加密的自定义压缩一样会失败,只是用户恰好在测加密。之前这一路径没有任何测试覆盖
  (同步分支有),所以 591→623 全绿也没挡住它。

## 修法

- 新增 `FileOperationDispatcher.performCustomCompression(sources:into:preferredName:format:mode:label:password:settings:control:) throws -> ArchiveCompressor.Report`:
  重算 `scopeTargets`(抽成 `static func scopeTargets(sources:destination:)`,与同步路径共用一份算法)、
  先做 `AuthorizedURLResolver.folderMatching` 前置校验(越权抛 `CustomCompressionFailure(message:)`,
  对话框直接显示这句)、再在 `FolderAuthorizationAccess.withAccesses(configuration: scopedConfig,
  persistRefreshedBookmark: persistenceHook())` 里调 `ArchiveCompressor.compress`。`.cancelled` 原样透传
  (「取消」不能变成红字)。`CustomCompressionSheet.save()` 改调它,不再直接调 `ArchiveCompressor.compress`。
- 顺带修**误导文案**:`ArchiveError.readFailed` 只由压缩器读源文件时抛,`ArchiveExtractor.describe` 却写作
  `Could not read the archive: …`,把排查方向带偏(像是压缩包坏了)。现在 = `Could not read “<文件>”: <系统原因>`;
  `sources.isEmpty` 改抛 `.writeFailed`。测试只断言 case 与「detail 里有文件名」,不受影响。
- 其它 deferred 写入已排查:`ArchiveRequestCenter` 只有压缩对话框一个生产者,解压「指定位置」走同步
  `withAuthorizations`,没有同类缺口。

## 验证(三层)

- 单测(3 个新用例,`MenuRightTests/FileOperationDispatcherTests.swift`):
  `testTheDialogWriteTakesItsOwnScopedAccess`(停请求 → 清空 spy → 调新方法 → 断言 `started == [authorized]`
  且 `stopped == [authorized]`,即写盘确实发生在 scope 里)、`testTheDialogWriteRefusesAPathOutsideAnyAuthorizedFolder`、
  `testTheDialogWriteKeepsTheCancellationIdentity`。
- **真沙箱端到端**(app 自测新增 `MENURIGHT_SELFTEST_ARCHIVE_DIALOG_CONFIRM=1` /
  `…_CONFIRM_PASSWORD=<密码>`;它调的就是 sheet 按钮那条路径,随后再**不走授权包装**读同一份源文件作负对照):
  `confirm=SUCCESS path=…/selftest-confirm.zip`,同一行的 `unscopedRead=DENIED(The file “selftest-source.txt”
  couldn’t be opened because you don’t have permission to view it.)` —— 这句话就是用户截图里的那句,证明
  「沙箱确实会拒」且「是这次取得的 scope 让写盘成立」。探针目录用的是已授权的 `/Users/suxin` 下的
  `~/MenuRight-ScopeProbe`(取证后已删除)。
- 外部实现:`/usr/bin/unzip` 无密码 → `unable to get password`;`unzip -P hunter2 -t` → `No errors detected`。

## 坑

- 用户目录 `/Users/suxin`(displayName `suxin`)本身就在授权列表里,所以 `~/Downloads/...` 的文件能通过
  dispatcher 的授权前置校验、却仍在写盘时被沙箱拒 —— 这正是「通过了校验但读不到文件」的指纹。
- `OperationArgs` 的参数顺序固定:`name` 必须写在 `sourcePaths` 之前(否则 `error: argument 'name' must precede argument 'sourcePaths'`)。
- 复现/取证用的探针目录务必删干净;app 自测的 PNG 仍只能写 App Group 容器。
