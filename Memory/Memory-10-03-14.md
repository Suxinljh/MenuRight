# 2026-10-03（第 14 轮）Dock 右键「退出」只关设置面板，只有菜单栏「退出」才结束整个服务

## 用户说了什么

原话：

> 「现在有个问题，就是我在底部的dock退出menuright后整个软件整体就退出了
> 我希望的是在dock右键menuright退出的是设置面板，而整个的右键服务和功能并不退出，
> 只有在顶部的状态栏退出的时候才退出整个服务和功能，这个可以调整吗」

附两张截图：菜单栏下拉（打开设置 ⌘, / 检查更新 / ─── / 退出 MenuRight ⌘Q）与 Dock 右键菜单（选项 / 显示所有窗口 / 隐藏 / 退出）。

## 问题根因

`MenuRight/App/MenuRightApp.swift` 里只有 `applicationShouldTerminateAfterLastWindowClosed`（关窗不退出），
**没有实现 `applicationShouldTerminate`**，于是 AppKit 的默认行为生效：Dock 图标的「退出」、⌘Q、应用菜单的「退出」
一律真的终止进程 → `MainAppIPCServer` 下线 → Finder 右键菜单每一项都以「主应用未运行」告终。

## 改了什么

### 1. 新规则放在可测的 `AppLifecycle` 里

`MenuRight/App/StatusMenu/AppLifecycle.swift`（新增成员，原 `terminatesAfterLastWindowClosed = false` 不动）：

```swift
static func shouldTerminate(
    intentionalQuitRequested: Bool,
    systemIsPoweringOff: Bool
) -> Bool {
    intentionalQuitRequested || systemIsPoweringOff
}
```

纯函数，测试 target 能直接编译断言（`MenuRightApp.swift` 持 `@main`，测试 target 编不了它，只能读源码守卫）。
原文档注释里「状态栏 退出（或 ⌘Q）是唯一的出路」已改：⌘Q 不再退出。

### 2. `AppDelegate`：拦截 + 只关设置窗口

`MenuRight/App/MenuRightApp.swift`：

- 新增状态：`private var quitRequested`（意图退出标记）、`private var systemIsPoweringOff`、`private var powerOffObserver`；
  新增 `func requestQuit() { quitRequested = true }`。
- `applicationWillFinishLaunching` 里订阅 `NSWorkspace.shared.notificationCenter` 的 `NSWorkspace.willPowerOffNotification`，
  置 `systemIsPoweringOff = true` —— 注销/重启/关机也走 terminate 请求，拦下会拖住关机。
- 新增 `applicationShouldTerminate(_:)`：`AppLifecycle.shouldTerminate(...)` 为假时记日志
  （`Self.log.notice` + `LifecycleDiagnostics.record`）、调 `dismissSettingsWindows()`、返回 `.terminateCancel`；
  为真时返回 `.terminateNow`。
- 新增 `dismissRegularWindows()`（初版叫 `dismissSettingsWindows`，因语义不准确改名）：只关
  `window.isVisible && !(window is NSPanel)` 的**常规窗口**（设置窗口，以及从它打开的自定义压缩对话框）。
  **面板一律留下**，否则更新提示/密码框/确认框（都是待决定的交互）会被顺手关掉。
- DEBUG 自测钩子（`runOpenTargetSelfTestIfRequested` / `runOpenTerminalSelfTestIfRequested` /
  `runSettingsSelfTestIfRequested` / `reportSelfTest` 共 4 处）在 `NSApp.terminate(nil)` 前先 `requestQuit()`，
  否则这些"跑完即退出"的钩子会被自己新增的规则拦下、永远退不出去。

### 3. 三处"意图退出"打标记

- `MenuRight/App/StatusMenu/StatusMenuView.swift`：新增 `private func quit()` →
  `(NSApp.delegate as? AppDelegate)?.requestQuit(); NSApp.terminate(nil)`；`case .quit` 的按钮改调 `quit()`。
- `MenuRight/App/Settings/SettingsRootView.swift` 的 `relaunch()`（重启应用）：替换实例已启动，退出是意图行为，
  也先 `requestQuit()` —— 否则旧实例留下，两个实例抢 IPC socket。
- 上面第 2 条的 4 个 DEBUG 自测点。

# 追加：真机测试报出的两个缺陷（同日第二轮）

## 用户说了什么（原话）

> 「测试发现
> dock上右键退出，只是关闭窗口，dock上依旧保持主程序活跃（左上角-应用程序名称-退出同理）
> 顶部状态栏的图标，鼠标左右键都无法唤起弹出」

（第一句是本次改造的预期行为，正确；第二句是回归缺陷。）

## 缺陷一：状态栏图标"看得见、点不开"

`dismissRegularWindows()` 初版扫 `NSApp.windows`、只排除 `NSPanel`，而 SwiftUI `MenuBarExtra` 的窗口是
**`NSStatusBarWindow`（`level = .statusBar` = 25，普通 `NSWindow`，不是 `NSPanel`）**，于是被 `close()` 掉：
图标还在，点击不再弹菜单。

自测清单（`build/rq-refusal-final.log`）实测到该窗口：

```
class=AppKitWindow        level=0   visible=true  panel=false title=MenuRight      ← 设置窗口
class=NSStatusBarWindow   level=25  visible=true  panel=false title=Item-0         ← 状态项窗口（被误关）
class=SheetPresentationWindow level=0 visible=true panel=false title=<none>
class=SPRoundedWindow     level=101 visible=false panel=false title=<none>
```

修法（不再"猜"窗口）：

- `AppLifecycle.mayDismiss(windowLevel:isVisible:isPanel:)` =
  `isVisible && !isPanel && windowLevel < NSWindow.Level.mainMenu.rawValue`
  （用 `<` 一个阈值而非 `== .normal`：自定义压缩对话框是 `level = .floating`(3)，限定 ==0 就关不掉它；
  阈值取 **`.mainMenu`(24)** 而不是 `.statusBar`(25)：写测试时发现 24 也 <25，菜单窗口会被放行，
  规则收紧到"菜单层级及以上一律不碰"）。
- 窗口改为显式登记：`MenuRightApp.swift` 新增 `SettingsWindowReader: NSViewRepresentable` + `WindowReportingView: NSView`
  （`viewDidMoveToWindow`）把设置窗口报给 delegate；`CustomCompressionDialogWindow.show/close` 登记 / 注销对话框窗口。
- `dismissRegularWindows()` 只遍历 `[settingsWindow, auxiliaryWindow]`，**不再 sweep `NSApp.windows`**。

## 缺陷二（更严重）：`NSApp.delegate` 不是我们的 delegate

自测打印揭示了真相：

```
SELFTEST settings-window-report class=AppKitWindow level=0 \
    delegate=SwiftUI.AppDelegate cast=false isAppDelegate=false gate=true
```

SwiftUI 把**它自己的 `SwiftUI.AppDelegate`** 装在 `NSApp.delegate`，只把部分回调转发给我们
`@NSApplicationDelegateAdaptor` 的 `AppDelegate`。于是全仓库 4 处 `(NSApp.delegate as? AppDelegate)` **一律 nil**：

| 位置 | 原本应有的作用 | 实际后果 |
| --- | --- | --- |
| `MenuRightApp.swift` 设置窗口登记 | 记住设置窗口 | 没登记 → 拒绝退出时什么都不关 |
| `StatusMenuView.quit()` | 打"意图退出"标记 | 菜单栏「退出」被自己的规则拦下 → **退不出去** |
| `SettingsRootView.relaunch()` | 同上 | 重启应用留下旧实例抢 IPC socket |
| `CustomCompressionDialogWindow.registerWithDelegate` | 登记对话框窗口 | 对话框不随设置窗口关闭 |

修法：新增 `MainAppGate` 协议 + `MainAppGateRegistry.gate`（`static weak var`，
`AppDelegate.init()` 里 `MainAppGateRegistry.gate = self` 发布），上述 4 处全部改走 registry。
协议放在 `AppLifecycle.swift`（app + test 两个 target 都编），所以 `CustomCompressionDialogWindow.swift`
不需要引用 app-only 的 `AppDelegate`。

## 缺陷三：`NSApp.terminate(nil)` 根本退不掉这个 app

实测（headless 与 `open -n` 真启动两种方式，均先打意图标记）：

- `NSApp.terminate(nil)`：进程继续活着，且 `applicationShouldTerminate` **完全没被调用**；
- `NSRunningApplication.current.terminate()`：返回 `true`，进程同样不退，且一次 15 秒延迟实验里 app 卡在
  "terminating pending" 状态、主队列不再处理块（log 空、进程仍在）。
- 对照：用户机上的安装版确实被 Dock 的「退出」调用到了 `applicationShouldTerminate`（诊断日志有
  `event=terminate refused (Dock/⌘Q)…`）——即 **AppleEvent 路径会转给我们，进程内直接 terminate 不会**。

修法：`MainAppGate` 只暴露 `quit()`，`AppDelegate.quit()` =
打标记 → `LifecycleDiagnostics.record` → `NSApp.terminate(nil)`（尽力）→ `quitGracePeriod = 0.75` 秒后
`finishQuitDirectly()`：记日志、`ipcServer.stop()`（与 `applicationWillTerminate` 同样的收尾）、`exit(0)`。
背景型 app 的「退出」若什么都不做，用户就再也退不出去了，所以必须保证这条兜底路径存在。

## 工程教训

- Xcode 的 debug dylib：`.../MenuRight.app/Contents/MacOS/MenuRight` 只有 45 KB，真实代码在
  `MenuRight.debug.dylib`（16.6 MB）。用 `strings` 查插桩字符串必须查 dylib，否则会误判"代码没编进去"。
- `open -n <app> --env KEY=1 -o log --stderr log` 可以给"真启动"的 app 传环境变量并收 stdout；
  但 stdout 重定向到文件后是**全缓冲**，进程被 kill 时日志会丢，判断是否退出要看 `pgrep`，不要只看日志。
- 无头（直接跑 Mach-O）与 `open` 启动在 AppKit terminate/AppleEvent 行为上不同，涉及生命周期的结论两种都要测。

## 收尾时发现的两件事

### 1. 规则阈值从 `.statusBar` 收紧到 `.mainMenu`

见上：纯规则测试发现 `mayDismiss(windowLevel: 24, …)`（`.mainMenu`）返回 `true`（24 < 25），
即"主菜单层级"的窗口仍会被关。规则改为 `windowLevel < NSWindow.Level.mainMenu.rawValue`，
菜单层级及以上（24/25/101）一律不碰。

### 2. 7z 固实归档在整包测试里偶发解不开（既存问题，非本轮引入）

本轮第一次全量跑（747 tests）有 4 个失败，其中两个与本次改动无关：

```
ArchiveModeAndSevenZipTests.swift:141 testEveryCompressingFormatGetsSmallerFromFastToMaximum
    sevenZip: the maximum-effort archive has to extract   (summary.failed == 3)
ArchiveModeAndSevenZipTests.swift:175-177 testSolidAndNonSolidBothRoundTrip
    solid 7z has to extract (failed == 3) / has to hold every file (written == 0)
```

- 失败**只出现在固实 7z**（同一测试里的非固实 7z、zip、gzip、bzip2 全部通过）；`failed == 3` 且 `written == 0`：
  固实归档共用一个数据块，解不开就是三个条目全输。
- 单独重跑 `-only-testing:MenuRightTests/ArchiveModeAndSevenZipTests` **连续 3 次全绿**（每次 20 tests）；
  `testSolidAndNonSolidBothRoundTrip` 在 `dock-quit`/`fix-p7`/`fix-p7b`/`fix-p7c` 四次历史全量跑里都是 passed；
  **本轮没有改动任何压缩/解压代码**。
- 同一天那次跑里 `testEveryCompressingFormatGetsSmallerFromFastToMaximum` 耗时 **44.7 秒**（平时几秒）——
  PLzmaSDK level 9 在整包负载下极慢；更早还见过体积断言的偶发失败（480 B 级别差几字节）。
  综合判断：**PLzmaSDK（LZMA2）在负载下不稳定**，不是本轮回归。
- 处置：**没有放宽固实解压断言**（那是真功能）。改为给这两处加解释性失败信息：
  `MenuRightTests/ArchiveModeAndSevenZipTests.swift` 新增私有 `failureReasons(_:)`
  （从 `ArchiveEntryOutcome.failed(String)` 取出"条目名: 原因"），断言消息里带上，下次复现能直接看到原因。
- 后续可做（未做）：给 `Encoder` 钉死线程数/字典大小（目前 `SevenZipWriter.archive` 没有调 `setNumberOfThreads`），
  或在写完 7z 后立刻用 `SevenZipContainer.info/open` 自校验一遍再落盘。
